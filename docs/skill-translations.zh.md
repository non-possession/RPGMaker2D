## to-prd

原文件：`/Users/mistluo/.codex/skills/to-prd/SKILL.md`

````markdown
---
name: to-prd
description: 将当前对话上下文转换成 PRD，并发布到项目的问题追踪器。当用户想基于当前上下文创建 PRD 时使用。
---

此 skill 会基于当前对话上下文和对代码库的理解产出一份 PRD。不要再访谈用户，只综合你已经知道的信息。

问题追踪器和分诊标签词汇应已提供给你；如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果还没有探索过仓库，先探索仓库，以理解代码库的当前状态。在整份 PRD 中使用项目的领域词汇表，并遵守你将触及区域里的所有 ADR。

2. 草拟为了完成实现需要构建或修改的主要模块。主动寻找可以抽取为深模块的机会，让它们能够被隔离测试。

深模块不同于浅模块，它会用一个简单、可测试、很少变化的接口封装大量功能。

向用户确认这些模块是否符合他们的预期。向用户确认他们希望为哪些模块编写测试。

3. 使用下面的模板编写 PRD，然后发布到项目的问题追踪器。应用 `needs-triage` 分诊标签，让它进入正常分诊流程。

<prd-template>

## 问题陈述

从用户视角描述用户正在面对的问题。

## 解决方案

从用户视角描述问题的解决方案。

## 用户故事

一份很长的编号用户故事列表。每条用户故事应采用以下格式：

1. 作为一个 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为一个手机银行客户，我想查看账户余额，以便我能更明智地决定自己的消费
</user-story-example>

这份用户故事列表应该极其充分，并覆盖该功能的所有方面。

## 实现决策

列出已经做出的实现决策。可以包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体文件路径或代码片段。它们很可能很快过时。

## 测试决策

列出已经做出的测试决策。包括：

- 对好测试的描述：只测试外部行为，不测试实现细节
- 哪些模块会被测试
- 测试的既有参考：例如代码库里相似类型的测试

## 不在范围内

描述本 PRD 明确不包含的事项。

## 其他备注

关于该功能的任何其他备注。

</prd-template>
````

````markdown
# 转换为 Issues

使用垂直切片，也就是示踪弹，将计划拆成可独立领取的问题。

问题追踪器和分诊标签词汇应已提供给你；如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从当前对话上下文中已有的内容开始。如果用户传入 issue 引用，例如 issue 编号、URL 或路径，作为参数，就从问题追踪器中获取它，并读取完整正文和评论。

### 2. 探索代码库（可选）

如果还没有探索过代码库，就先探索，以理解代码当前状态。Issue 标题和描述应使用项目的领域词汇表，并遵守你将触及区域里的 ADR。

### 3. 草拟垂直切片

将计划拆成**示踪弹** issue。每个 issue 都是一个很薄的垂直切片，端到端穿过所有集成层，而不是某一层的水平切片。

切片可以是 `HITL` 或 `AFK`。`HITL` 切片需要人工交互，例如架构决策或设计评审。`AFK` 切片可以在没有人工交互的情况下实现并合并。尽可能优先选择 `AFK`。

<vertical-slice-rules>
- 每个切片都交付一条狭窄但完整的路径，贯穿每一层（schema、API、UI、测试）
- 完成后的切片可以单独演示或验证
- 优先拆成多个薄切片，而不是少量厚切片
</vertical-slice-rules>

### 4. 向用户确认

以编号列表展示建议的拆分。对每个切片展示：

- **标题**：简短描述性名称
- **类型**：HITL / AFK
- **被阻塞于**：哪些其他切片必须先完成（如果有）
- **覆盖的用户故事**：它对应哪些用户故事（如果源材料中有）

询问用户：

- 粒度感觉是否合适？太粗还是太细？
- 依赖关系是否正确？
- 是否有切片应该合并或进一步拆分？
- 哪些切片标为 HITL 和 AFK 是否正确？

迭代直到用户批准拆分。

### 5. 将 issues 发布到问题追踪器

对每个批准的切片，向问题追踪器发布一个新 issue。使用下面的 issue 正文模板。应用 `needs-triage` 分诊标签，让每个 issue 进入正常分诊流程。

按依赖顺序发布 issue，先发布阻塞项，这样可以在 “Blocked by” 字段引用真实 issue 标识符。

<issue-template>
## 父项

父 issue 在问题追踪器中的引用（如果源材料本身是已有 issue；否则省略本节）。

## 要构建什么

对此垂直切片的简明描述。描述端到端行为，而不是逐层实现。

## 验收标准

- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

## 被阻塞于

- 阻塞 ticket 的引用（如果有）

如果没有阻塞项，则写：“None - can start immediately”。

</issue-template>

不要关闭或修改任何父 issue。
````

````markdown
---
name: tdd
description: 使用红-绿-重构循环进行测试驱动开发。当用户想用 TDD 构建功能或修复 bug、提到“red-green-refactor”、想要集成测试，或要求测试优先开发时使用。
---

# 测试驱动开发

## 哲学

**核心原则**：测试应该通过公共接口验证行为，而不是验证实现细节。代码可以完全改变；测试不应该因此改变。

**好测试**是集成风格的：它们通过公共 API 运行真实代码路径。它们描述系统做什么，而不是怎么做。一个好测试读起来像规格说明，例如“用户可以用有效购物车结账”，它会准确说明系统具备什么能力。这些测试能经受重构，因为它们不关心内部结构。

**坏测试**会耦合到实现。它们 mock 内部协作者，测试私有方法，或通过外部方式验证，例如直接查询数据库而不是使用接口。警告信号是：你重构时测试失败，但行为并没有改变。如果你重命名一个内部函数，测试就失败，那么这些测试测的是实现，不是行为。

参见 [tests.md](tests.md) 获取示例，参见 [mocking.md](mocking.md) 获取 mocking 指南。

## 反模式：水平切片

**不要先写所有测试，再写所有实现。** 这是“水平切片”：把 RED 当成“写完全部测试”，把 GREEN 当成“写完全部代码”。

这会产生**糟糕的测试**：

- 批量写出的测试测的是想象中的行为，而不是真实行为
- 你最终会测试事物的形状，例如数据结构、函数签名，而不是面向用户的行为
- 测试会对真实变化失敏：行为坏了时仍通过，行为没问题时却失败
- 你会跑得太超前，在理解实现前就承诺测试结构

**正确做法**：通过示踪弹做垂直切片。一个测试 -> 一个实现 -> 重复。每个测试都响应你从上一个循环中学到的东西。因为你刚写完代码，所以你确切知道什么行为重要，以及如何验证。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED->GREEN: test1->impl1
  RED->GREEN: test2->impl2
  RED->GREEN: test3->impl3
  ...
```

## 工作流

### 1. 规划

探索代码库时，使用项目的领域词汇表，让测试名称和接口词汇与项目语言一致，并遵守你将触及区域里的 ADR。

写任何代码之前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测试哪些行为，并排序优先级
- [ ] 识别 [深模块](deep-modules.md) 的机会：小接口，深实现
- [ ] 为 [可测试性](interface-design.md) 设计接口
- [ ] 列出要测试的行为，而不是实现步骤
- [ ] 获得用户对计划的批准

询问：“公共接口应该长什么样？哪些行为最重要、最需要测试？”

**你不可能测试所有东西。** 与用户精确确认哪些行为最重要。把测试精力集中在关键路径和复杂逻辑上，而不是每一种可能边界情况。

### 2. 示踪弹

写一个只确认系统一件事的测试：

```
RED:   为第一个行为写测试 -> 测试失败
GREEN: 写通过测试所需的最少代码 -> 测试通过
```

这就是你的示踪弹：证明路径能端到端跑通。

### 3. 增量循环

对每个剩余行为：

```
RED:   写下一个测试 -> 失败
GREEN: 写通过测试所需的最少代码 -> 通过
```

规则：

- 一次只写一个测试
- 只写足够通过当前测试的代码
- 不预判未来测试
- 让测试聚焦于可观察行为

### 4. 重构

所有测试通过后，寻找 [重构候选](refactoring.md)：

- [ ] 抽取消除重复
- [ ] 加深模块：把复杂性移到简单接口后面
- [ ] 在自然合适处应用 SOLID 原则
- [ ] 思考新代码揭示了现有代码的什么问题
- [ ] 每一步重构后都运行测试

**永远不要在 RED 状态下重构。** 先到 GREEN。

## 每个循环的检查清单

```
[ ] 测试描述行为，而不是实现
[ ] 测试只使用公共接口
[ ] 测试能经受内部重构
[ ] 代码对当前测试来说足够最小
[ ] 没有添加推测性功能
```

````

## diagnose

原文件：`/Users/mistluo/.codex/skills/diagnose/SKILL.md`

````markdown
---
name: diagnose
description: 面向复杂 bug 和性能回归的有纪律诊断循环。复现 -> 最小化 -> 提出假设 -> 加仪器观测 -> 修复 -> 回归测试。当用户说“diagnose this”/“debug this”、报告 bug、说某物坏了/抛错/失败，或描述性能回归时使用。
---

# 诊断

用于处理困难 bug 的纪律。只有在明确说明理由时才跳过阶段。

探索代码库时，使用项目的领域词汇表来建立相关模块的清晰心智模型，并检查你将触及区域里的 ADR。

## 阶段 1 — 建立反馈循环

**这就是此 skill 的核心。** 其他一切都是机械过程。如果你有一个快速、确定、agent 可运行的 bug 通过/失败信号，你就会找到原因；二分、假设测试和仪器观测都只是消费这个信号。如果没有这样的信号，盯着代码看再久也救不了你。

在这里投入不成比例的精力。**要积极。要有创造力。拒绝放弃。**

### 构建反馈循环的方法，按大致顺序尝试

1. **失败测试**，放在任何能触及 bug 的接缝上：单元、集成、端到端。
2. 针对运行中的开发服务器的 **Curl / HTTP 脚本**。
3. 使用固定输入夹具的 **CLI 调用**，并把 stdout 与已知良好快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，并断言 DOM/console/network。
5. **重放捕获的 trace。** 将真实网络请求、payload 或事件日志保存到磁盘；在隔离环境中通过代码路径重放。
6. **一次性 harness。** 启动系统的最小子集，例如一个服务和 mock 依赖，用一次函数调用触发 bug 代码路径。
7. **属性 / fuzz 循环。** 如果 bug 是“有时输出错误”，运行 1000 个随机输入，寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间，例如 commit、数据集、版本，自动化“在状态 X 启动、检查、重复”，这样可以运行 `git bisect run`。
9. **差分循环。** 将相同输入跑过旧版本与新版本，或两套配置，并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 驱动这个人，让循环仍然结构化。捕获的输出会反馈给你。

建立正确的反馈循环，bug 就修好了 90%。

### 迭代反馈循环本身

把这个循环当作一个产品。一旦你有了一个循环，就问：

- 能不能让它更快？缓存 setup、跳过无关初始化、缩小测试范围。
- 能不能让信号更锋利？断言具体症状，而不是“没有崩溃”。
- 能不能让它更确定？固定时间、固定随机种子、隔离文件系统、冻结网络。

一个 30 秒且不稳定的循环只比没有循环好一点。一个 2 秒且确定的循环是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压力、缩窄时序窗口、注入 sleep。50% 复现率的 flaky bug 可以调试；1% 不行。持续提高复现率，直到它可调试。

### 当你真的无法建立循环

停下来，并明确说明。列出你尝试过什么。向用户请求：(a) 能复现问题的环境访问权，(b) 捕获的工件，例如 HAR 文件、日志 dump、core dump、带时间戳的录屏，或 (c) 添加临时生产仪器观测的许可。**不要**在没有循环的情况下继续提出假设。

在你拥有一个可信的循环之前，不要进入阶段 2。

## 阶段 2 — 复现

运行循环。看见 bug 出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是附近碰巧出现的另一个失败。错 bug = 错修复。
- [ ] 失败能在多次运行中复现；对于非确定性 bug，则以足够高的比例复现，足以进行调试。
- [ ] 你已经捕获确切症状，例如错误信息、错误输出、慢耗时，以便后续阶段验证修复确实解决了它。

在复现 bug 之前不要继续。

## 阶段 3 — 提出假设

在测试任何假设之前，生成 **3-5 个排序后的假设**。只生成一个假设会让你锚定第一个看似合理的想法。

每个假设都必须是**可证伪的**：说明它会做出什么预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它变得更糟。”

如果你无法说出预测，这个假设就是感觉；丢弃它，或把它磨锋利。

**在测试前把排序列表展示给用户。** 他们通常有领域知识，能立刻重新排序，例如“我们刚部署了与 #3 相关的变更”，或知道哪些假设已经被排除。这是便宜的检查点，能省很多时间。不要因此阻塞；如果用户不在，就按你的排序继续。

## 阶段 4 — 加仪器观测

每个探针都必须映射到阶段 3 中的某个具体预测。**一次只改变一个变量。**

工具偏好：

1. 如果环境支持，优先使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界处加**定向日志**。
3. 永远不要“把所有东西都打日志然后 grep”。

**给每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。结束时清理会变成一次 grep。没打标签的日志会幸存；打标签的日志要死。

**性能分支。** 对性能回归而言，日志通常是错工具。改为：建立基线测量，例如计时 harness、`performance.now()`、profiler、query plan，然后二分。先测量，再修复。

## 阶段 5 — 修复 + 回归测试

在修复前写回归测试，但前提是存在**正确接缝**。

正确接缝是指：测试会以调用点实际发生的方式触发**真实 bug 模式**。如果唯一可用接缝太浅，例如 bug 需要多个调用方但测试只有单调用方、单元测试无法复现触发 bug 的链条，那么在这里写回归测试会带来虚假的信心。

**如果不存在正确接缝，这本身就是发现。** 记录它。代码库架构正在阻止这个 bug 被锁定。把这点标记给下一阶段。

如果存在正确接缝：

1. 把最小化复现转换成该接缝上的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 针对原始、未最小化场景重新运行阶段 1 的反馈循环。
````

````markdown
# 改进代码库架构

暴露架构摩擦，并提出**加深机会**：把浅模块重构为深模块。目标是可测试性和 AI 可导航性。

## 词汇表

在每条建议中都精确使用这些术语。语言一致就是重点；不要漂移到“component”“service”“API”或“boundary”。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **模块**：任何拥有接口和实现的东西，函数、类、包、切片都可以。
- **接口**：调用方为了使用模块必须知道的一切：类型、不变量、错误模式、顺序、配置。不只是类型签名。
- **实现**：内部代码。
- **深度**：接口上的杠杆：小接口背后有大量行为。**深** = 高杠杆。**浅** = 接口几乎和实现一样复杂。
- **接缝**：接口所在的位置；一个无需原地编辑就能改变行为的地方。使用这个词，而不是“边界”。
- **适配器**：满足某个接缝处接口的具体事物。
- **杠杆**：调用方从深度中获得的东西。
- **局部性**：维护者从深度中获得的东西：变化、bug、知识集中在一处。

关键原则（完整列表见 [LANGUAGE.md](LANGUAGE.md)）：

- **删除测试**：想象删除这个模块。如果复杂性消失了，它只是透传。如果复杂性会在 N 个调用方中重新出现，它就在发挥作用。
- **接口就是测试表面。**
- **一个适配器 = 假设性的接缝。两个适配器 = 真实接缝。**

此 skill 会受到项目领域模型的启发。领域语言为好的接缝命名；ADR 记录此 skill 不应重新争论的决策。

## 流程

### 1. 探索

先阅读项目的领域词汇表，以及你将触及区域里的所有 ADR。

然后使用 Agent 工具并设置 `subagent_type=Explore` 来遍历代码库。不要遵循僵硬启发式；有机地探索，并记录你感受到摩擦的地方：

- 理解一个概念是否需要在许多小模块之间来回跳转？
- 哪些模块是**浅**的：接口几乎和实现一样复杂？
- 哪些纯函数只是为了可测试性而被抽出来，但真正的 bug 藏在它们如何被调用的地方，也就是缺少**局部性**？
- 哪些紧耦合模块会跨过它们的接缝泄漏？
- 代码库哪些部分没有测试，或很难通过当前接口测试？

对任何你怀疑很浅的东西应用**删除测试**：删除它会集中复杂性，还是只是移动复杂性？“是，会集中”就是你想要的信号。

### 2. 展示候选项

展示一份编号的加深机会列表。每个候选项包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么造成摩擦
- **解决方案**：用普通语言描述会改变什么
- **收益**：用局部性和杠杆解释，也说明测试会如何改善

**用 CONTEXT.md 的词汇描述领域，用 [LANGUAGE.md](LANGUAGE.md) 的词汇描述架构。** 如果 `CONTEXT.md` 定义了“Order”，就说“Order intake 模块”，不要说 “FooBarHandler”，也不要说 “Order service”。

**ADR 冲突**：如果某个候选项与现有 ADR 矛盾，只有当摩擦真实到值得重启该 ADR 时才提出它。清晰标记，例如：“_与 ADR-0007 矛盾，但值得重开，因为……_”。不要列出每个被 ADR 禁止的理论重构。

此时不要提出接口。询问用户：“你想探索其中哪一项？”

### 3. 拷问循环

用户选择一个候选项后，进入拷问式对话。和他们一起走完整棵设计树：约束、依赖、加深后模块的形状、接缝背后放什么、哪些测试能够保留下来。

随着决策逐渐清晰，副作用要内联发生：

- **以 `CONTEXT.md` 中不存在的概念命名加深后的模块？** 将该术语加入 `CONTEXT.md`，遵循与 `/grill-with-docs` 相同的纪律（见 [CONTEXT-FORMAT.md](../grill-with-docs/CONTEXT-FORMAT.md)）。如果文件不存在，懒创建。
- **在对话中磨清楚一个模糊术语？** 立刻更新 `CONTEXT.md`。
- **用户用一个承重理由拒绝候选项？** 提供记录 ADR 的选项，措辞为：“要我把这记录成 ADR 吗？这样未来架构评审就不会再次建议它。” 只有当这个理由真的需要被未来探索者知道，以避免重复建议同一件事时才提供；跳过短暂理由，例如“现在不值得”，以及显而易见的理由。见 [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md)。
- **想探索加深模块的替代接口？** 见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。
````

````markdown
## 流程

### 1. 探索

查看当前仓库以理解起始状态。读取已有内容；不要假设：

**部分 A — 问题追踪器。**

> 说明：“问题追踪器”是本仓库 issue 存放的地方。`to-issues`、`triage`、`to-prd` 和 `qa` 等 skills 会读写它；它们需要知道应该调用 `gh issue create`、在 `.scratch/` 下写 markdown 文件，还是遵循你描述的其他 workflow。请选择本仓库实际追踪工作的地方。

> 说明：当 `triage` skill 处理传入 issue 时，它会让 issue 通过一个状态机：需要评估、等待报告者、准备好给 AFK agent 领取、准备好给人类、或不会修复。为了做到这一点，它需要应用与你实际配置相匹配的标签或等价物。如果你的仓库已经使用不同标签名，例如 `bug:triage` 而不是 `needs-triage`，就在这里映射它们，避免 skill 创建重复标签。

- `ready-for-human`：需要人类实现
- `wontfix`：不会被处理
````
